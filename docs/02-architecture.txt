## 1. Architecture Overview
==============================================================================

```
SCREENS (PIN lock, Sales area, Admin area) -> LOGIC (pricing, bills, ledger, returns, purchases, expenses)
   -> DATABASE ON THE PHONE (Room / SQLite, tested migrations, entries never edited, no network)
PRINTER (58 mm) and EXPORT (CSV files via the share menu) hang off the screens and the database.
VERSION 2 (parked): server and database, sync, laptop dashboard, monthly dashboard, costing, separate logins.
```

### 1.1 Principles

- Version 1 is local-first. One Android handheld holds all the data. There is no server and no network. The release app declares no INTERNET permission.
- One Owner, two areas. After the PIN the Owner switches between the Sales area and the Admin area. The areas are separate in code, so version 2 can give them to different people.
- Money is integer cents. Never floating point. Material quantities are Long milli-units.
- Entries are never edited or deleted. A bill is voided, a purchase or expense is reversed by a linked entry.
- The database is never wiped. From the first real release every change to its structure is a tested migration, never a destructive one.
- Demo code lives only in the debug source set. A release app starts with reference data only.
- The table shapes follow the server design (UUID ids, cents, immutable entries), so version 2 can import the version 1 export.

## 4. Data Model
==============================================================================

### 4.1 Conventions

- Primary key: UUID v4 on every table, so version 2 can import the data.
- Money columns end in _cents (Long). Cost per chapathi is a Long in ten-thousandths of a dollar. Material quantities are Longs in milli-units (1,000 = 1 g, 1 ml or 1 piece). Wastage is stored in basis points (200 = 2%). No floats.
- Times are stored as UTC epoch milliseconds. Month grouping uses the phone's time zone.
- No update or delete methods exist for bills, bill items, payments, returns, purchases, expenses or production damage. The only change is a bill going active to void. A test scans the DAO interfaces.
- Every table is declared in Room with a version number and an exported schema.

### 4.2 Tables

| Table | Key fields | Rules |
|---|---|---|
| Reference CustomerType | id, name, salesman_can_edit_price, is_active | Restaurant, Shop, Retail, Catering. Switch defaults: Retail and Catering ON. Changes are logged. |
| Product | id, code, name, standard_packet_size (12), yield_per_kg (32), is_active | Packing cost comes from the packing material. |
| Customer | id, name, location, type_id, phone, address, payment_mode (cash or credit), is_corporate, opening_balance_cents, notes, is_active | Unique on name plus location (ignoring case and spaces). Walk-in is not a row. |
| PriceDefault | id, product_id, customer_type_id, unit_price_cents (per standard packet), effective_from | History kept. A newer row needs a later date. |
| PriceOverride | id, customer_id, product_id, unit_price_cents, effective_from, note, is_active | Beats PriceDefault. |
| Setting | key, value | owner_name, device_code, business_name, address lines, phone, footer_text, wastage_bp, lock_minutes, pin_hash, pin_salt, next_bill_seq, next_receipt_seq. |
| Billing Invoice | id, number (unique), customer_id (null for walk-in), customer_name, customer_location, is_corporate, salesman_name, issued_at, total_cents, status (active or void), void_reason, voided_at | Immutable except active to void. |
| InvoiceItem | id, invoice_id, product_id, product_name, qty_packets, chapathis_per_packet, unit_price_cents (charged, per packet), list_price_cents, price_overridden, line_total_cents | Price is a snapshot. line_total = qty_packets x unit_price. |
| Payment | id, receipt_number, customer_id (null for walk-in), invoice_id (optional), amount_cents, method (cash, zelle, check, card, other), paid_at, note | Append-only. |
| ReturnRecord | id, customer_id, invoice_id (optional), product_id, qty_packets, chapathis_per_packet, reason, resolution (credit or replacement), unit_price_cents, credit_cents, occurred_at, note | Credit reduces balance. Replacement does not. |
| Materials Material | id, name, base_unit (g, ml or piece), purchase_unit, base_per_purchase_unit, is_packing | Wheat, oil, sugar, salt, baking powder, potassium sorbate, packing. |
| MaterialPurchase | id, material_id, purchased_on, qty_milli, total_paid_cents, note, reverses_id (optional), reason (required when reversing) | Add-only. A mistake is corrected by a linked reversing row. A row is reversed once; a reversal is never reversed. |
| OpeningStock | id, material_id, month (YYYY-MM), qty_milli, value_cents | Set once per material. |
| RecipeItem | id, product_id, material_id, qty_milli_per_kg_wheat | Wheat is a material with 1,000 g as the basis. Potassium sorbate only on Mamre Chapathi. |
| ProductionDamage | id, product_id, damaged_on, chapathis, note | Add-only. Counts in material usage. |
| ExpenseCategory, Expense | category: id, name, kind (direct or indirect). Expense: id, category_id, expense_date, amount_cents, description, reverses_id, reason | Add-only with reversing entries. |
| ChangeLog | id, at, what, before_text, after_text | Written for price changes, price-switch changes, voids, settings changes, customer edits. |
| PaymentAllocation | id, payment_id, invoice_id, amount_cents | Optional in version 1: oldest-first allocation can be derived from bills and payments. |
| Version 2 only User, Device, MonthLock, SyncBatchLog | not in the version 1 database | Come with the server. |

### 4.3 Invariants (must always hold)

| ID | Invariant |
|---|---|
| I-1 | No floating point for money or quantities anywhere. |
| I-2 | line_total_cents = qty_packets x unit_price_cents (price per packet). Bill total = sum of line totals. Where a price is derived (a custom packet default), round half up in integer arithmetic. |
| I-3 | Bill number is unique and matches ^MAM-[A-Z0-9]+-[0-9]{4,}$. The sequence is saved in the same transaction as the bill and never reused. |
| I-4 | Bills and their items never change after saving, except status active to void in the Admin area. |
| I-6 | Balance = opening + non-void bills - credits - payments. Always computed, never stored as editable. |
| I-7 | The price used is the one held when the bill was made, stored on the line with the list price. |
| I-8 | The Sales area and every printed bill contain no cost, profit or expense data. |
| I-9 | No deletes of bills, payments, returns, purchases, expenses or damage. |
| I-13 | A line's price may differ from the list price only if the customer type's switch is on; the change is stored as price_overridden. Above 0 and at most 10 times the list price. |
| I-14 | Purchases, expenses and damage are never edited or deleted. A correction is a linked reversing row with a reason. |
| I-15 | A migration never deletes or recreates user data. Destructive migration is forbidden after the first real release. |
| I-16 | A corporate customer's balance is never built into a bill, a payment receipt or any Sales-area screen. |

## 5. Local Storage, Migrations and Export
==============================================================================

### 5.1 Database and migrations

- One Room database, mamre.db. Schemas are exported to android/app/schemas and committed.
- Every schema change is a numbered, written migration with a test that opens the old schema, migrates, and checks the data survived. No destructive migration from the first real release (I-15).
- All writes go through use cases in one transaction. DAOs expose no update or delete for protected tables (I-9).

### 5.2 First run (release build)

A release app starts with reference data only: the four customer types with their price-edit switches; the two products (standard packet 12, yield 32); the materials list; the recipe per 1 kg of wheat (wheat 1 kg, oil 80 ml, sugar 20 g, salt 15 g, baking powder 2 g; sorbate unset); the expense categories; and default settings (business name Mamre Foods, device code W1, wastage 2%, lock after 5 minutes). It has no customers, prices, bills or demo data. The debug build seeds demo data from src/debug. The first screen asks the Owner to choose a PIN.

### 5.3 Export to files

- Admin area, Export: writes one CSV per table plus manifest.txt (data version, export time, row counts): customers, customer_types, products, prices, invoices, invoice_items, payments, returns, materials, purchases, expenses, production_damage, settings (PIN excluded), change_log.
- UTF-8, header row, UUIDs, money in cents, quantities in milli-units, times in ISO 8601.
- The Owner shares the files with the Android share sheet or saves them to a folder he picks.
- There is no import in version 1. Version 2 imports these files.

## 6. PIN Lock and Local Security
==============================================================================

- At first run the Owner chooses a PIN of 4 to 6 digits. It is stored only as a salted PBKDF2 hash. The plain PIN is never stored or logged.
- The app locks after the number of minutes in Settings (default 5) and whenever it has been in the background longer than that. Five wrong PINs in a row add a growing delay.
- The Owner can change the PIN while unlocked. There is no PIN recovery in version 1. A forgotten PIN means clearing the app's data, which deletes everything (Doc 1 A-26). The Owner should choose a PIN he will remember.
- The Sales and Admin areas are separate navigation graphs with a route guard. Cost and profit data is not shown anywhere in version 1.
- The release app requests no INTERNET permission, so no data can leave the phone except through an export the Owner starts. Export files are plain text with customer data: share them only with people you trust.
- The database is not encrypted beyond Android's own device encryption. Set a screen lock on the phone.
- Android backups of the app are turned off, so nothing is copied to the cloud behind the Owner's back.

## 7. Printing Design
==============================================================================

- Interface ReceiptPrinter { suspend fun print(doc): PrintResult } with MockPrinter (an on-screen preview, used until P-1 is solved) and the handheld's own library once the model is known.
- The bill layout is a pure function: bill data in, a list of text lines out, 32 characters wide for a 58 mm printer (verify on the real device). It is tested with golden files.
- Order of operations: save the bill, then print. A print failure shows Retry and Reprint and never loses the bill.
- The header comes from Settings. No business detail is written in the code (Doc 1 A-31).

## 8. Release, Signing and Updates
==============================================================================

- Make one signing key once, with a strong password, and keep the key file and the password in two safe places outside the repository. The key is never committed. If it is lost, an update cannot install over the old app, and the data is lost (Doc 1 A-30).
- Every release raises the version code. An APK signed with the same key installs over the old app and keeps the data.
- Install: copy the APK to the phone, allow 'install unknown apps' for the file manager or browser, open the APK. Never uninstall the app; uninstalling deletes all its data.
- Before each release: run all tests, build the release APK, unzip it and confirm it contains no fake API, demo credentials, demo seed data or demo address (this check is a required acceptance test).
- Tag each release in git (v1.0.0 and so on) and keep the signed APK of each release.
- An install guide (one page, with pictures) is part of the release.

## 11. Costing Engine Specification
==============================================================================

>> [VERSION 1 AND VERSION 2]
> The costing engine is built and tested, but the Costing screen and the Dashboard are hidden in version 1 (Doc 1 A-28). Version 1 stores every input; version 2 shows the results.

The module costing/engine.py is pure: it takes plain data in and returns plain data out, with no database access. The formulas are in Doc 1 section 9.

```
material_usage(material, month):                 # milli-units, one rounding step, half up
    chapathis[p] = sum(line.qty_packets * line.chapathis_per_packet
                       for non-void invoice lines of product p in month)
                   + replacement_chapathis[p] + damaged_chapathis[p]
    qty = sum(chapathis[p] * recipe_milli_per_kg[p, material] / yield_per_kg[p] for p)
    if material.is_packing: return packets_invoiced + replacement_packets   # no wastage
    return qty * (10000 + wastage_bp) / 10000

price(material, month):                          # weighted average
    if opening_qty + bought_qty == 0: return INCOMPLETE
    return (opening_value + purchases_value) / (opening_qty + bought_qty)

cost_consumed(material, month) = material_usage * price     # INCOMPLETE if no price
direct_expense(month)          = sum(cost_consumed over all materials)
closing_stock(material)        = opening + bought - used    # warn if negative

indirect_per_chapathi(month):
    net = chapathis_invoiced(month) - chapathis_credited(month)
    if net == 0: return NOT_ALLOCATED
    return total_indirect_expenses(month) / net
```

- Missing material price, missing recipe item or missing sorbate quantity: result is INCOMPLETE with a list of what is missing. Never treat as zero.
- Compute in integers. Round only once per figure and only where Doc 2 section 4.1 says.
- Golden tests: (1) 12,000 chapathis, wastage 2%: wheat used 382.5 kg; 400 kg bought for $440.00 gives $1.10 per kg, cost consumed $420.75, closing stock 17.5 kg. (2) A standard 12-chapathi packet at the Doc 1 section 9.7 prices gives $0.5475, $0.6975 and $0.8475. (3) A custom 6-chapathi packet gives $0.2738 ingredients and $0.4238 direct.

## 12. Testing and Acceptance
==============================================================================

| Area | Required tests |
|---|---|
| Pricing | Override beats default. Missing price blocks the sale. Snapshot survives a later price change. Custom packet price rounds half up (250 per 12 gives 208 for 10 chapathis and 188 for 9). Walk-in uses Retail. |
| Price editing | A locked type cannot change a price even if the screen is bypassed. An editable type stores the list price and price_overridden. Above 0 and at most 10 times the list price. |
| Ledger | Doc 1 section 6.5 example. Void bills are excluded. A return credit reduces the balance. Overpayment becomes credit. |
| Corporate account | No balance on the bill, payment receipt, payment step, confirm screen or customer card, while the Admin ledger still counts it. Tests look at the builders' data and the layout. |
| Database | A migration test per schema version keeps data. No DAO method updates or deletes a protected table. First run creates reference data only. |
| Lock and PIN | A wrong PIN is refused. Only a salted hash is stored. The app locks after the set time. |
| Export | Every table is written. Row counts match the app. The PIN is never exported. |
| Materials and costing | Golden cases in section 11. Purchases never edited or deleted. A reversing entry nets out. Negative stock warns. A missing price gives INCOMPLETE. Packing excludes damaged chapathis. |
| Printing | Golden files at 32 columns for the corporate bill, the normal credit bill, the cash walk-in bill and the payment receipt. A print failure keeps the bill. |
| Release build | The release package contains no fake API, no demo logins, no demo data and no demo address. |

Manual check before real use: make bills of every kind on the real handheld, print them, void one, export, and check the balances against the paper.
