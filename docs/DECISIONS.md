2026-10-02 - A2 review fix (finding 5): a walk-in invoice is validated together with ALL payments that reference it BEFORE anything is stored. Only payments that pass full validation count toward the total: valid amount and bounds, a valid method, a note when method is other, and no customer_id (a walk-in has no customer, so a customer_id is customer_mismatch or unknown_customer). If the counted payments do not add up to exactly the invoice total (under or over), the invoice is rejected with walkin_not_fully_paid and its payments are rejected: a payment that is itself invalid gets its own validation error, every other one gets invoice_rejected (retryable false). Nothing for that walk-in is stored. Replaces the earlier walk-in line, which counted unvalidated payments and could store an unpaid walk-in (Doc 1 s4.1). Re-review: a payment id that is already stored never counts toward a walk-in (it is answered duplicate for its original invoice), so only NEW valid payments in the push must add up exactly.
2026-10-02 - A2 review fix (finding 6): lock order rule: every sales writer takes the SalesCounter lock (next_sales_version) FIRST, then locks or writes any other sales row. void_invoice now takes the counter first and then select_for_update on the invoice (it did it the other way round, which could deadlock with a payment holding the counter). One fixed order means no deadlock between writers; the order is documented in next_sales_version and tested from the query log for store_invoice, store_payment and void_invoice (Doc 2 s6.4).
2026-10-02 - A2 re-review fix (finding 3): Meta.base_manager_name = "objects" on Invoice, InvoiceItem, Payment and PaymentAllocation (and the abstract base), so _base_manager is the guarded manager and update, delete, bulk_update and bulk_create through it are refused too. Django's own save() and delete machinery use _update, _insert and the delete collector, not these queryset methods, so inserts, the void update and related lookups still work (tested). This is a state-only change, so it is migration sales 0002_guard_base_manager (sales 0001 is not merged yet). The guards still protect the ORM only; database-level protection is a P7 question in QUESTIONS.md.
2026-10-02 - A2 re-review fix (finding 2): void_permit reads accounts.AuditLog directly (one existence check by pk, imported lazily) because accounts has no selector for it; it is a read, not a write, and no accounts file was changed. Add an accounts selector later if the owner prefers.
2026-10-02 - A2 narrow-review fix (finding 2): void_permit now also needs, from the database row (not the instance): a user who is right now an active admin (accounts.selectors.is_active_admin), a non-empty void_reason in after_json, an age of at most 60 seconds, and an invoice that is still active (so a row works once); plus the earlier checks (real AuditLog, action invoice.void, entity invoice, entity_id equals the invoice pk).
